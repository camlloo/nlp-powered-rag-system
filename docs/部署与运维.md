# 部署与运维手册

版本 V1.0　编制日期 2026 年 11 月 7 日　配套实现文档 V1.1

## 1 部署拓扑

**开发环境**：Windows 侧单 API 进程 + 单 worker 进程；PostgreSQL 17 + pgvector 0.8 运行在 WSL docker 容器 `pgvector`（端口 5433→5432）；上传原文件由 MinIO 保存，本机 endpoint `127.0.0.1:9000`，桶 `nlprag`。本地无需推理 GPU，模型经百炼兼容接口调用。

**生产建议**：API 与 worker 分进程部署，数据库与 MinIO 使用独立、持久化的存储；两个进程必须连接同一 MinIO 服务和桶，并使用一致的凭证及传输配置。`127.0.0.1` 指各进程自身的回环地址，跨容器或跨主机时需改为双方都能访问的地址。多 API 进程各自持有内存索引缓存，总占用需预算（每进程上限 `INDEX_CACHE_BUDGET_MB`，默认 256 MiB，§13.1）。限制同时构建的知识库数量，避免新旧快照占满内存。

## 2 上线步骤（对应实现文档 §12.2）

1. 固定 PostgreSQL 与 pgvector 版本及镜像摘要（`pgvector/pgvector:pg17`），记录 `SELECT version();` 与 `SELECT extversion FROM pg_extension WHERE extname='vector';` 输出；准备持久化的 MinIO 实例与 `nlprag` 桶，确认 API 和 worker 均可访问并具备所需对象读、写、删除权限。
2. 建库：`CREATE DATABASE nlp_rag ENCODING 'UTF8' TEMPLATE template0;`，pgvector 扩展由首版迁移自动安装。
3. 安装依赖：`uv sync`；配置 `cp .env.example .env` 并填写 `API_TOKEN`、模型凭证（`MODEL_BASE_URL`、`DASHSCOPE_API_KEY`）与 MinIO 设置。API 和 worker 使用相同的 MinIO 配置；敏感凭证由环境或密钥管理注入，勿提交 `.env`。生产环境模型凭证缺失会直接报 `model_auth_error`，不会静默回落 Mock。
4. 旧库升级前，先按下文「旧数据切换」停止写入、盘点并备份旧库与旧原文件。执行迁移：`uv run alembic upgrade head`（迁移前置确认 vector 扩展可用）；数据库迁移由独立任务执行，不在多个 API 进程启动时同时执行。
5. 如从本地文件版本切换，先按本节「旧数据切换」处理旧本地文件及对应数据库记录，再启动新版本。此选择不迁移旧文件，影响文档须在切换后重新上传。
6. 初始化种子数据：`uv run python -m scripts.seed`；能力验证：`uv run python -m scripts.verify_db`。
7. 启动：`uv run uvicorn app.main:app`（API）与 `uv run python -m app.workers`（worker）。`GET /healthz` 是存活探针；`GET /readyz` 检查数据库与 pgvector 扩展，不调用付费模型，也不检查 MinIO 或 worker。就绪探针通过不代表原文件可读写：应另行验证 MinIO 连接、桶及读写权限，确认 worker 能读取原文件并完成导入/重建。
8. **升级到 0004（去知识库化）注意**：迁移会把既有知识库的存活文档合并进单一「主空间」并清除旧索引/任务，随后排队一条全量重建任务——升级后必须启动 worker 完成重建，重建完成前问答返回 `insufficient_evidence`。reindex 会重新解析原文件；对于继续保留的文档，其 MinIO 对象必须存在且可读取。按本方案清除的旧本地文档不能靠重建恢复，应重新上传。qa_* 审计记录中的旧 kb_id 保留为历史值。

### 旧数据切换

本次选择**彻底删除旧本地上传文件及其对应数据库记录，不迁移到 MinIO**。切换前停止 API、worker 和其他写入方，盘点旧文件、文档及版本记录和相关任务/索引引用，明确将受影响的范围；确认业务方接受原文、记录及相关检索结果无法直接恢复的后果。按第 4 节的一致恢复点原则备份数据库和旧版本 `STORAGE_DIR/uploads`（默认 `data/uploads`），并验证恢复；该目录仅用于旧数据切换，不是新版本存储位置。之后由授权运维人员根据实际数据依赖实施删除；不得直接删除仍被其他数据引用的记录，也不要把切换视为保留旧文档的迁移。核对旧文件及对应记录已清除后重建索引，重新上传仍需使用的文档。备份保留或销毁应遵守组织的数据保留与彻底删除要求。

旧数据盘点脚本 `scripts/purge_legacy_uploads.py` 仅提供只读预览，不提供执行删除的功能；其清单不是自动删除许可，也可能无法覆盖所有历史路径或审计引用。实际清除必须先解决共享索引、任务、引用、缓存和部分失败恢复等问题，不要把逻辑删除或数据库迁移当作已完成物理清除。

### 原文件对象与删除风险

原文件对象键为 `YYYY/MM/DD/用户ID/文件名去扩展名/原始文件名`，例如 `2026/11/07/123/报告/报告.pdf`；日期为服务端本地日期，文件名仅去掉最后一个扩展名。数据库保存不含凭据的对象 URI（`s3://<bucket>/<URL 编码 key>`），原文不存入数据库。相同对象键已存在时采用**先删后传**，删除后上传失败可能导致旧原文件无法恢复；这不是原子替换，也不能依赖数据库回滚找回对象。重要文件应事先做好独立备份并验证恢复能力。删除和保留期清理可能物理删除 MinIO 原对象；原文一旦删除，解析及全量重建无法再读取该文件，操作前应确认引用范围与备份状态。

### 对象写入屏障与清理的保守语义

固定对象键可被同名上传覆盖，MinIO 又不是原子条件创建，故上传与后台清理共用 PostgreSQL 行锁的持久屏障表 `upload_object_guard`（迁移 0006）：

- **上传**：先在独立事务把该 URI 的屏障由 `ready` 置为 `writing`、失效全部共用此键的旧文档并递增各知识库 `data_revision`（排队重建），提交成功后才 `DELETE`+`PUT`；对象写入完成后在新事务登记文档、版本、任务并把屏障转回 `ready`。SDK 客户端已针对审定版本禁用自动重试与重定向、PUT 强制单分片；`safe_mutation_no_retry` 不成立时上传直接返回 503，绝不静默覆盖。
- **结果不确定即永久阻断**：对象请求异常、进程退出或末次提交不确定时，屏障保持 `writing`，同名后续上传返回 409「需人工核查」，不自动补偿、不盲删、不自动重试。运维须确认远端请求确已结束（可查 MinIO 访问日志/对象状态）后再处置。
- **后台清理**：逐版本在全局复核同 URI 引用与屏障状态，只有能证明对象仍属于待删版本时才删除；对缺少屏障的历史对象、构建中快照、保留期内软删除目标、以及无法安全删除的 KB 父记录，抛出 `CleanupDeferred`（可重试或需人工），**不会把部分完成谎报为成功**。
- **worker 不自动重排**：现有 worker 把失败/延迟的清理任务标记为 `failed`，不按保留期周期重新入队；`revision_changed` 同理。生产需外部定时任务按知识库补投 cleanup/reindex 作业。`127.0.0.1:9000` 指各进程自身回环地址，API 与 worker 必须连同一 MinIO 服务、桶与凭证配置。

`GET /readyz` 仅检查数据库与 pgvector，不探测 MinIO、worker 或屏障表；就绪不等于原文件可读写，切换后应另行做隔离桶读写与上传→索引→问答联调。

| --- | --- | --- |

| MinIO | `MINIO_ENDPOINT/MINIO_BUCKET/MINIO_ACCESS_KEY/MINIO_SECRET_KEY/MINIO_SECURE` | endpoint、桶、用户名、密钥与 TLS 开关；API 与 worker 保持一致 |

| 模型 | `MODEL_BASE_URL/DASHSCOPE_API_KEY/EMBEDDING_MODEL/EMBEDDING_DIM/CHAT_MODEL/MODEL_TIMEOUT_SECONDS` | 百炼接入；`EMBEDDING_DIM` 启动强校验 1024 |
| 网关 | `RETRY_*`、`MODEL_*_BUDGET`、`EMBEDDING_INPUT_MAX_BYTES` | 重试/预算/输入预算 |
| 切块 | `CHUNK_*`、`EMBEDDING_TITLE_PREFIX_CHARS` | 规则切块参数，参与流水线指纹 |
| 解析 | `FALLBACK_ENCODING/MAX_PDF_PAGES/PDF_*` | 解析限制与质量阈值（需真实样本校准） |
| 检索 | `BM25_K1/BM25_B/CHANNEL_TOP_K/RERANK_TOP_K/MMR_LAMBDA/EVIDENCE_*` | 检索与门槛（占位阈值待校准） |
| 运维 | `WORKER_*/INDEX_CACHE_BUDGET_MB/CLEANUP_RETENTION_HOURS` | 租约、缓存预算、保留期 |

本机 MinIO 配置示例（用户名为占位符，密钥从安全渠道单独注入；不要将真实凭证写入仓库）：

```dotenv
MINIO_ENDPOINT=127.0.0.1:9000
MINIO_BUCKET=nlprag
MINIO_ACCESS_KEY=<用户名>
MINIO_SECURE=false
```

`MINIO_SECRET_KEY` 由部署环境或密钥管理提供，不在文档中填写。`MINIO_SECURE=false` 仅用于本机未启用 TLS 的环境；生产使用 TLS 时改为 `true` 并配置可访问的地址。确保 API 与 worker 获得相同配置。

## 4 备份与恢复

- 数据库备份示例：`wsl docker exec pgvector pg_dump -U postgres nlp_rag > backup_$(date +%F).sql`。同时独立备份 MinIO 的 `nlprag` 桶及其全部原文件对象；只备份数据库或 MinIO 一方都不足以恢复文档。
- 为获得一致恢复点，暂停上传、删除和后台清理等写入，待进行中的任务结束后再备份数据库与桶；记录同一恢复点和对象清单。恢复时先恢复配套的数据库和桶，再核对文档版本的 `storage_uri` 与对象，以及对象内容与 `kb_document_version.file_sha256`。若使用不停机备份，须自行保证两者恢复点一致并验证结果。
- **恢复演练**：`uv run python -m scripts.backup_drill` 自动执行数据库 pg_dump 往返、核心表行数核对、活跃快照向量列抽样文本比对，并清理演练库（`DRILL_KEEP=1` 可保留）；它不替代 MinIO 桶备份及对象恢复验证。首次部署与每次大版本升级后，另行演练桶恢复并核对对象与数据库记录。
- 建议 RPO 24 小时 / RTO 4 小时；启用 WAL 归档可缩短数据库 RPO，但对象存储也须满足目标。恢复后重启 API 与 worker，从数据库重建 BM25 与向量缓存；检查 `GET /readyz`，并验证 MinIO 原文件读取及 worker 导入/重建后恢复服务。

## 5 管理员操作速查

认证方式：`X-API-Token: <API_TOKEN>` 或 `Authorization: Bearer <token>`。接口文档 `http://127.0.0.1:8000/docs`。

管理员引导路径：前端登录页「管理员令牌」页签输入 `API_TOKEN` 进入后台 → 「用户管理」把注册用户提升为管理员（数据库内 `is_admin=true`，此后可走 JWT）。系统始终保留最后一名管理员（撤销时 409）。

**数据组织（去知识库化）**：文档直接归属「个人」或「某组织」，并设公开/私有——组织公开=所有人可检索；组织私有=上传者与该组织成员；个人公开=所有人；个人私有=仅上传者。内部由单一「主空间」承载（kb_id 为实现细节，`POST /kbs` 拒绝保留名、主空间不可删除）。

| 操作 | 命令 |
| --- | --- |
| 上传文档（产品面） | `POST /api/v1/documents`（multipart：`file` + `scope`=personal 或组织名 + `visibility`=public/private；支持 `Idempotency-Key`；同内容重复上传返回 200+duplicate） |
| 文档清单（产品面） | `GET /api/v1/documents?scope=all|personal|组织名`（仅返回当前用户可见文档，含归属与可见性字段） |
| 删除文档 | `DELETE /api/v1/documents/{id}`（逻辑删除；上传者本人或管理员，或原知识库 editor；检索立即失效） |
| 改归属/可见性 | `PATCH /api/v1/documents/{id}` `{"scope":"组织名或personal","visibility":"public|private"}`（两者至少其一；上传者本人或管理员；块级冗余列同步并递增 `acl_revision`，检索可见范围即时生效） |
| 全量重建（产品面） | `POST /api/v1/admin/reindex`（管理员专用，重建主空间索引） |
| 查处理状态 | `GET /api/v1/jobs/{job_id}`（status + stage + error_code；上传者可查自己的任务） |
| 问答 | `POST /api/v1/qa` `{"question":"...","history":[],"top_k":6}`（kb_id 可缺省=主空间；`conversation_id` 可空=归入会话） |
| 问答（流式） | `POST /api/v1/qa/stream`（SSE：meta → citations → delta* → done/notice/error；需 worker 常驻运行以处理索引任务） |
| 会话列表 | `GET /api/v1/conversations?limit=20&offset=0`（当前用户，按最近更新排序） |
| 新建会话 | `POST /api/v1/conversations` `{"title":"..."}`（标题=首个问题，前端自动创建） |
| 会话详情 | `GET /api/v1/conversations/{id}`（由 qa_request 审计还原消息与引用） |
| 删除会话 | `DELETE /api/v1/conversations/{id}`（审计行保留） |
| 检索调试 | `POST /api/v1/retrieval/debug`（kb_id 可缺省；双路召回/融合/重排/门槛指标明细） |
| 引用详情 | `GET /api/v1/citations/{citation_id}`（文档级可见性复核） |
| 反馈 | `POST /api/v1/feedback` `{"request_id":"...","rating":"helpful","reason":"..."}` |
| 组织标签清单 | `GET /api/v1/admin/org-tags`（含用户数与活跃文档数） |
| 建组织标签 | `POST /api/v1/admin/org-tags` `{"name":"研发部"}`（重名 409） |
| 重命名标签 | `PATCH /api/v1/admin/org-tags/{id}` `{"name":"..."}` |
| 删组织标签 | `DELETE /api/v1/admin/org-tags/{id}`（剥离文档/块引用与用户关联；受影响知识库递增 `acl_revision` 触发运行时索引重载；该组织文档退回上传者个人归属） |
| 用户清单 | `GET /api/v1/admin/users?limit=50&offset=0` |
| 授予/撤销管理员 | `PATCH /api/v1/admin/users/{id}` `{"is_admin":true}` |
| 替换用户标签 | `PUT /api/v1/admin/users/{id}/org-tags` `{"tag_ids":[1,2]}`（整体替换，即时影响可见性） |

内部机制接口（前端不使用，供脚本与测试）：`POST /api/v1/kbs`、`POST /api/v1/kbs/{id}/documents`、`GET /api/v1/kbs/{id}/documents`、`POST /api/v1/kbs/{id}/reindex` 等知识库面端点继续可用。

任务状态机：queued → running（stage: parse → chunk → embed → validate → publish）→ succeeded / failed。`needs_review` 属于文件解析结果，`superseded` 属于索引状态，二者不在同一字段（§9.4）。

## 6 监控要点（实现文档 §11）

日志为 JSON 格式，以 `request_id`（HTTP）与 `job_id`（任务）关联。重点观测：
- 导入成功率、解析失败率（`jobs.error_code` 分布：`parse_failed` / `lease_expired` / `revision_changed`）；
- 队列等待与索引发布耗时（ingest_job 时间戳差）；
- 检索耗时（retrieval debug 的 `gate` 指标与延迟日志）、缓存占用（`INDEX_CACHE_BUDGET_MB`）；
- 模型错误率与 token 用量（qa_request.usage_json / model_budget_exceeded 出现频次）；
- 拒答率与用户反馈（qa_request.answer_status 分布 + qa_feedback）。

日志不记录正文与密钥；API 错误响应统一 `code/message/request_id/retryable`。
