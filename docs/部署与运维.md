# 部署与运维手册

版本 V1.0　编制日期 2026 年 11 月 7 日　配套实现文档 V1.1

## 1 部署拓扑

**开发环境**（本仓库默认形态）：Windows 侧单 API 进程 + 单 worker 进程；PostgreSQL 17 + pgvector 0.8 运行在 WSL docker 容器 `pgvector`（端口 5433→5432）。本地无需推理 GPU，模型经百炼兼容接口调用。

**生产建议**：API 与 worker 分进程部署，数据库独立实例；多 API 进程各自持有内存索引缓存，总占用需预算（每进程上限 `INDEX_CACHE_BUDGET_MB`，默认 256 MiB，§13.1）。限制同时构建的知识库数量，避免新旧快照占满内存。

## 2 上线步骤（对应实现文档 §12.2）

1. 固定 PostgreSQL 与 pgvector 版本及镜像摘要（`pgvector/pgvector:pg17`），记录 `SELECT version();` 与 `SELECT extversion FROM pg_extension WHERE extname='vector';` 输出。
2. 建库：`CREATE DATABASE nlp_rag ENCODING 'UTF8' TEMPLATE template0;`，pgvector 扩展由首版迁移自动安装。
3. 安装依赖：`uv sync`；配置 `cp .env.example .env` 并填写 `API_TOKEN`、模型凭证（`MODEL_BASE_URL`、`DASHSCOPE_API_KEY`）。生产环境凭证缺失会直接报 `model_auth_error`，不会静默回落 Mock。
4. 执行迁移：`uv run alembic upgrade head`（迁移前置确认 vector 扩展可用）。
5. 初始化种子数据：`uv run python -m scripts.seed`；能力验证：`uv run python -m scripts.verify_db`。
6. 启动：`uv run uvicorn app.main:app`（API）与 `uv run python -m app.workers`（worker）。探针：`GET /healthz`（存活）、`GET /readyz`（就绪，检查数据库与 pgvector 扩展，不调用付费模型）。
7. 数据库迁移由独立任务执行，不在多个 API 进程启动时同时执行。

## 4 备份与恢复

- 备份命令（容器内）：`wsl docker exec pgvector pg_dump -U postgres nlp_rag > backup_$(date +%F).sql`；原文件目录 `STORAGE_DIR/uploads` 独立备份，二者通过 `kb_document_version.file_sha256` 核对。
- **恢复演练**：`uv run python -m scripts.backup_drill`——自动执行 pg_dump 往返、核心表行数核对、活跃快照向量列逐块文本比对，并清理演练库（`DRILL_KEEP=1` 可保留）。首次部署与每次大版本升级后各执行一次。
- 建议 RPO 24 小时 / RTO 4 小时；启用 WAL 归档可缩短 RPO。恢复后重启 API 与 worker，从数据库重建 BM25 与向量缓存，`GET /readyz` 通过后恢复服务。

## 5 管理员操作速查

认证方式：`X-API-Token: <API_TOKEN>` 或 `Authorization: Bearer <token>`。接口文档 `http://127.0.0.1:8000/docs`。

| 操作 | 命令 |
| --- | --- |
| 建知识库 | `POST /api/v1/kbs` `{"name": "..."}` |
| 上传文档 | `POST /api/v1/kbs/{id}/documents`（multipart；支持 `Idempotency-Key`；同内容重复上传返回 200+duplicate） |
| 查处理状态 | `GET /api/v1/jobs/{job_id}`（status + stage + error_code） |
| 文档清单 | `GET /api/v1/kbs/{id}/documents?include_deleted=false` |
| 删除文档 | `DELETE /api/v1/documents/{id}`（逻辑删除；检索立即失效；物理清理按保留期异步） |
| 全量重建 | `POST /api/v1/kbs/{id}/reindex` |
| 检索调试 | `POST /api/v1/retrieval/debug`（双路召回/融合/重排/门槛指标明细） |
| 问答 | `POST /api/v1/qa` `{"kb_id":1,"question":"...","history":[],"top_k":6}` |
| 引用详情 | `GET /api/v1/citations/{citation_id}` |
| 反馈 | `POST /api/v1/feedback` `{"request_id":"...","rating":"helpful","reason":"..."}` |

任务状态机：queued → running（stage: parse → chunk → embed → validate → publish）→ succeeded / failed。`needs_review` 属于文件解析结果，`superseded` 属于索引状态，二者不在同一字段（§9.4）。

## 6 监控要点（实现文档 §11）

日志为 JSON 格式，以 `request_id`（HTTP）与 `job_id`（任务）关联。重点观测：
- 导入成功率、解析失败率（`jobs.error_code` 分布：`parse_failed` / `lease_expired` / `revision_changed`）；
- 队列等待与索引发布耗时（ingest_job 时间戳差）；
- 检索耗时（retrieval debug 的 `gate` 指标与延迟日志）、缓存占用（`INDEX_CACHE_BUDGET_MB`）；
- 模型错误率与 token 用量（qa_request.usage_json / model_budget_exceeded 出现频次）；
- 拒答率与用户反馈（qa_request.answer_status 分布 + qa_feedback）。

日志不记录正文与密钥；API 错误响应统一 `code/message/request_id/retryable`。
